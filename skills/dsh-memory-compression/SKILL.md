# dsh-memory-compression

## 路径约定（按自己机器替换）

| 占位符 | 含义 |
|---|---|
| `<DSH_HOME>` | DSH 主目录，默认 `~/.dsh`（Windows 为 `%USERPROFILE%\.dsh`）；环境变量 `DSH_HOME` 即其绝对路径 |
| `<TOOLS>` | 辅助脚本目录。**由本包自带**，位于包的 `tools/`；复制到 `<DSH_HOME>/tools/` 或直接用包内路径皆可（清单与用法见文末「辅助脚本」） |
| `<WEB>` | DSH Web 基址，默认 `http://127.0.0.1:3080`（以环境变量 `DSH_WEB_URL` 为准） |
| `<TRACK>` | 目标注入轨文件：`<DSH_HOME>/memories/MEMORY.md`（全局）、`…/USER.md`（用户）、`…/projects/<hash>/KEY.md`（项目关键） |

## 何时用

- 某条**注入轨**（memory / user / key）大到每回合往系统提示词灌数万字符，要在**不丢事实**的前提下压缩它。
- 要做**过期审计**（去掉已被更新条目否定的旧说法）——见第 2.7 步，它可与压缩同批做，也可单独做。
- 只做小轨重写、归档、日常清理 → 用 `dsh-memory-curation`（单轨文件机制：分块、归档、注入自检）。本技能专管**大数据量压缩流水线**。

## 第 0 步：先量，再动手

```
node <TOOLS>/check-inject.js <TRACK>
```

输出**渲染字符数**（该轨每回合真实注入量）与连续左花括号计数。逐轨量一遍，才知道重量在哪一条。**量级参照**：小工作区的 key 轨常在数千字符级，而长期未整理的大型工作区可到 **10 万字符**——两者差两个数量级，前者不必动。

三条容易搞错的前提：

- **只有注入轨花 token**。`projects/<hash>/MEMORY.md`（项目日志）与 `daily/<日期>.md` 都不注入——压它们只省磁盘，别当成 token 优化报功。
- 判据：渲染 > 20k 字符的轨值得动；> 90k 的轨等于每回合 3-5 万 token。
- **`check-inject.js` 报 THROW 要分清「正在毒」还是「潜伏毒」**：它渲的是整份文件，而摘要注入开着时正文根本不注入。实测过这样的情形：某轨正文里有一处连续左花括号、脚本判 THROW，但该轨 `keyProgressiveDisclosure=auto` 且条目数远超全量阈值，实际只注入摘要行、工作区并没瘫。**别据此宣布工作区已坏，也别据此判它没事**——阈值一调小或改成全量注入就当场致命。同理，**摘要行本身必须单独扫一遍**：摘要行带毒才是真致命。

## 第 1 步：把「整理」与「摘要注入」分开（B 与 A）

- **A = 量级手段**：`keyProgressiveDisclosure` 默认 `off`（始终全量注入）。改成 `auto`/`on` 后每回合只注入「一行摘要 + 可 expand 的 id」，细节按需 `memory action=expand id=<mem-xxxxxxxx>`。**降幅 10-20 倍**。
- **B = 质量手段**：合并条目、剔除被取代的旧口径、**给每条补 `[summary:…]`**。A 的摘要模式读的正是这一行——B 不做，摘要就退化成正文首行的粗暴截断。
- **顺序：先 B 后 A**。先理顺事实、补好摘要，再开摘要注入。
- A 的落法（运行期接口，热生效、**不需重启**）：

```
curl -s --noproxy '*' -X POST <WEB>/memory-evolve/api/config \
  -H "Content-Type: application/json" \
  --data-binary '{"patch":{"keyProgressiveDisclosure":"auto","keyFullInjectThreshold":12,"keyFullInjectCharLimit":12000}}'
```

读当前值：`GET <WEB>/memory-evolve/api/config`。运行期配置落盘在 `<DSH_HOME>/memories/plugin-state.json`——**不是**插件自身的 `update-state.json`（后者是 git 更新检查状态：schemaVersion / repoPath / status / lastError 那一套；两者并存、内容完全不同，很容易写错落点）。

- **`auto` 的判据要读清**：`条目数 ≤ keyFullInjectThreshold` **且** `总字符 ≤ keyFullInjectCharLimit` 才全量，否则摘要。默认阈值极小——想做到「小轨全量、大轨摘要」必须同时把两个阈值调大，否则连几千字符的小轨也会被切摘要。
- 改配置属「改运行方式」，先向用户报备再动手。

## 第 2 步：压缩流水线（B 的六步）

### 2.1 快照与基线

把整个 `memories` 目录快照到 `<DSH_HOME>/memories/_archive/snapshot-<日期>/`（含各 `projects/<hash>/` 下的 KEY.md、MEMORY.md）。同时记四组基线：文件字节数、条目数、渲染字符数、内容 SHA256。**这些是后面判断「有没有丢事实」「有没有被并发回写」的唯一依据。**

### 2.2 并发保全（最容易翻车的一步）

目标工作区**可能正有别的会话在跑**（判据：项目 `MEMORY.md` 的 mtime 是几分钟内；实测过「快照后 3 分钟内被另一会话追加数百字节」）。于是：

- 快照之后写进来的条目**一条都不能覆盖**。
- 装配时**现读现盘**，按内容哈希 diff：凡快照里没有的条目，一律**逐字保留、不参与任何合并**，原样附在新文件末尾。
- 落盘后**立即复读**条目数与字节数；若被并发回写（数字对不上），直接重做一次。

### 2.3 按主题切块

- **不要按顺序切**，按主题切：同一块内才会有可合并的重复与取代关系。
- 每块 25-40KB（约 1 万 token 输入，子代理不会撑爆上下文）。
- 先扫一遍全部条目标题，人工分组，再用脚本按编号抽块。
- 块文件头部写 manifest：`原始条目编号（按正文出现顺序）：…`，供子代理回报覆盖映射。

### 2.4 并行子代理合并

一块一个子代理，一次性并发派出（6 块左右可行）。指令必须自带全部约束（子代理看不到主对话）：

```
输入：<chunk 文件>；输出：<merged 文件>；覆盖表：<cov 文件>
1) 通读全部条目，按主题合并成尽可能少的条目。
2) 绝不丢失事实：口径、铁律、定论、数值、公式、ID、编号、路径、命令、文件名、
   覆盖率、日期、被推翻的旧结论、教训，都要在合并稿里能找到。宁可留冗余，不许删事实。
3) 后条推翻前条时只保留最新说法，并在该处标注（旧版见 KEY-archive.md）。
4) 保留定位事实的时间：句首/句末用 [09-15] 这类简写日期。
5) 输出格式：条目之间是单独一行 §；每条第一行 [summary:不超过 120 字]（摘要内不得出现
   右方括号，也不得出现连续两个左花括号）；第二行 [该条最早原始日期 YYYY-MM-DD] 标题（合并原 N 条）。
6) 覆盖表：每行「原条目 <编号> → 合并稿第 <k> 条」；被完全取代的写「已被取代（并入第 <k> 条）」。
   本块编号必须一个不漏。
7) 只写这两个文件，不要碰输入文件。
```

### 2.5 客观校验——**不要相信回报**

子代理都会说「已自检通过」，要用机械校验兜底（`<TOOLS>/verify-merge.js`、`<TOOLS>/verify-hard.js`）：

- **令牌级覆盖率**：从原文提取标识符（`[A-Za-z_][A-Za-z0-9_.\-/]{2,}`）与 ≥2 位数字，做「源 → 稿」集合差。
- **必须再做分段判定**：把缺失令牌按 `/ . -` 拆段，若每段都还在稿里，判**软缺**（只是写法差异，例如 `a/b/c` 改写成顿号连接、`BOSS 2.6` 对 `BOSS2.6`、字段名加了前缀）。只有硬缺才叫丢事实。不做这一步，误报会淹掉真问题。
- 把硬缺令牌**定位回原条目编号**，交给对应子代理定向修复——这是第二轮，只补漏、不重压比例。

### 2.6 装配与落盘

- 合并稿按块序拼接 + 快照之外的新增条目逐字保留（见 2.2）。
- **落盘前四项安全检查**：① 全文无连续两个左花括号；② 每条都有 `[summary:…]`；③ 新增条目数 = 现盘条目数 − 快照条目数；④ 条目数确实减少了。任一项不过就拒绝写盘。
- 先写 staging 文件并 `check-inject.js` 量一遍，**拿到落盘后的真实渲染字符数**再动真文件。
- 落盘时：① 备份 `KEY.md.bak-premerge-<时间戳>`；② 被合并掉的原文**逐字追加**进 `KEY-archive.md`（带一段说明头），可随时移回；③ 写新文件；④ 复读校验。
- 现成脚本：`<TOOLS>/assemble-and-swap.js`（默认演练，加 `--write` 才动盘）；小轨单文件重写继续用 `curate.js`。

### 2.7 过期审计：去掉被更新条目否定的旧说法

合并只挑事实、不判时效，所以「后条推翻前条」的旧文会长期留在轨里（甚至还留在**被注入的摘要行**里）。要单独做一遍**时效审计**。判据只有一条：**后条明文否定了前条**——「作废 / 已取代 / 已更正 / 已落地 / 已裁定 / 旧数」，或事实被后来的实现改写（「待定案」→已裁定、「有意推迟·未实现」→已落地）。**只是细化、补充、换措辞的不算**；宁少报，不可错报。

1. **先建索引**：按单独一行 § 切块，抽「编号 + 日期 + 摘要」列表。日期以条目自带的日期为准，**不是文件位置**——主题化压缩过的轨里位置与时间已经脱钩。实测大型轨上同日两条互相打架的例子不止一处（一条明写「已定案、替代此前待校准」，而位置更靠后的另一条还写着「待校准」）。
2. **跨块判定**：否定者常在几百行之外，所以**每块子代理都要拿到全部条目的摘要索引**，否则它只看得见局部、报出一堆假否定。
3. **自己复核每一条候选**：子代理会把「细化」升格成「否定」（实测：某分片报 4 处，其中 1 处只是数据说明与后续裁定的关系，不是否定）。逐条读原文再定，别照单执行。
4. **整条归档 vs 逐句改写**：真正能整条归档的极少（实测某轨 67 条里 0 条）；绝大多数是**条内某几句被否定**，同一条里还并存着成立的口径与过期的水位。逐句改写时：
   - 只替换被否定的那一句，**其余字符一个不动**（字面替换脚本，别重打整个条目）；
   - 旧句**逐字**追加进 `KEY-archive.md`；
   - 摘要行 `[summary:…]` 若也载有被否定的说法，**必须同步改**——摘要注入开着时摘要行是唯一真正注入的东西：正文里的错读者看不到，摘要里的错每回合都进上下文。
   - 被否定的是「未做/待定案」清单时，改写要**只撤销已兑现的那几项**，其余未做项原样留着（实测：某条的 10 项待实现里 6 项已落地、4 项仍未做）。
5. **落盘**：字面替换天然并发安全（别的新增条目不会命中旧句），但仍要在写盘前复读一次比对基线；脚本要对**每一处**校验「唯一命中」与「新文双花括号为 0」，任一不过就整体拒写。

现成脚本：`<TOOLS>/unexpire.js`——替换表外置在 `edits.json`（格式见 `tools/edits.example.json`），逐处字面替换 + 唯一命中校验 + 归档追加 + 复读校验；默认空跑，加 `--write` 才落盘。

实测一例（某项目 key 轨，67 条 / 198KB）：查出 20 处明文否定，逐句改写后**条目数不变（67）**、字节 198,291→200,300、双花括号 1→0、`check-inject.js` 由 THROW 变 OK。

## 第 3 步：对收益要有诚实预期

高熵技术事实（命令行、参数、字段名、数值、公式、覆盖率）在**零丢事实**约束下的实测压缩下限约 **70-90%**，即只能降 10-30%——某次 6 块分别停在 79%-89%。**不要承诺 30-45%**，也不要为凑比例删事实。要**量级**下降只能靠 A（摘要注入）。

另外：**压缩与过期审计别混成一个功劳**。A 开着时压正文只省磁盘、不省 token；过期审计省的是**正确性**（让模型不再读到已被推翻的口径），它通常还让文件变**大**（实测 +2,009 字节）。

## 坑（都是实测踩过的）

1. **子代理会在最后写回报时失败/中断**，产物却已经写好。先查输出文件（存在、字节数合理、条目可解析）再决定重派，别盲目重跑。
2. **校验快照会过时**：`hard-missing.json` 生成于修复前，而文件在修复中被重写过——30 个「缺失」里 18 个其实已在。**修复后必须重跑校验**再下结论。
3. **分词误报**三类：连写（`a/b/c`）、大小写（`DSH` vs `dsh`）、带前缀/后缀的完整名（`tile` vs `tile_forbidden`）。全部落在「软缺」里，分段判定即可筛掉。
4. **summary 行长死限**：不超过 120 字且不得含右方括号。子代理经常超限，落盘前后都要机械复检、逐条压。
5. **`[日期] [summary:…]` 是合规写法**：插件 `parseEntrySummary` 会先剥掉 `[id]`/`[日期]`/`[git …]`/`[branch:…]`/`[dsh-only]` 头部标记，再要求紧跟 `[summary:…]`。自写检查时别写死成行首匹配，否则误报「缺摘要」——**真踩过**：一个只认行首 `[summary:` 的索引脚本，把 20 多条合规条目全报成「缺摘要」，据此得出的结论全错。
6. **覆盖表是子代理自述，可能错**：实测某块的覆盖表把一条「已被取代」写错（其实内容完整落在另一条），映射也有错位，靠内容回核才纠正。覆盖表只作线索，冲突时以正文为准。
7. **归档能力有差异**：archive 只支持 memory / user / key 三轨；`project` 轨没有归档，重写前必须先手动备份。
8. **双花括号铁律**照旧：任何写进注入轨或技能 frontmatter/正文的文本，都不得出现连续两个左花括号。**非注入轨（项目日志 / daily）里也建议一并清掉**——它不会立刻致命，但会被后续「复制条目进注入轨」的动作原样搬过去。
9. **项目日志不做过期审计**：`projects/<hash>/MEMORY.md` 是按时间追加的日志，「后条推翻前条」正是它的价值（取证链）。只清里面的毒源与明显笔误，**不要**按 2.7 去删它的旧条目。

## 完成判据

- `check-inject.js` 报该轨渲染字符数下降（若只做过期审计，则报 OK 且双花括号计数 0 即可，字符数可能上升）；
- 快照之外的新增条目一条未丢（哈希比对），被合并/被否定的原文能在 `KEY-archive.md` 逐字找回；
- 所有条目都有 ≤120 字的 `[summary:…]`；
- A 的配置改动可从 `GET <WEB>/memory-evolve/api/config` 读到，并已落 `<DSH_HOME>/memories/plugin-state.json`；
- 向用户回报四个数：文件字节、条目数、**每回合渲染字符数**（压缩前 / 压缩后 / 开摘要后）、**被判定过期的处数**（并列出你**故意没动**的可疑项及理由）。

## 辅助脚本（本包自带，位于包的 `tools/`）

把 `tools/` 里的脚本复制到 `<DSH_HOME>/tools/`，或直接用包内路径调用；下面用 `<TOOLS>` 指代其所在目录。
`tools/` 自带一个内容为 `{"type": "commonjs"}` 的 `package.json`：这些脚本是 CommonJS，脱离本包复制到别处时，若目标目录属于一个 ESM 包会报 `require is not defined`——连这个 `package.json` 一起复制即可。

| 脚本 | 用途与用法 |
|---|---|
| `check-inject.js <轨文件>` | 复刻 DSH 的提示词插值渲染该轨：打印 OK/THROW、连续左花括号计数、**渲染字符数**（该轨每回合真实注入量）。THROW 退出码 1；找不到 `@deepseek-ai/dsh-system-prompt` 时退出码 3，并提示用 `DSH_SYSTEM_PROMPT_MODULE` 指定其 `lib/index.js` |
| `check-summaries.js <轨文件>` | 不渲染的格式体检：缺 `[summary:…]` 的块、摘要超 120 字、摘要含右方括号、连续左花括号计数、块数与字节 |
| `curate.js <src> <keepCsv\|-> <newEntries\|-> <archive>` | 按单独一行 § 分块；`keepCsv` 为要原样保留的块序号（1 起算，`-` 表示一块不留）；被移除块的原文追加进归档件 |
| `track-index.js <轨文件>` | 打印每块的 `编号 \| 日期 \| 字节 \| 标题` 索引（过期审计第 1 步建索引用） |
| `track-summaries.js <轨文件>` | 打印每块的摘要行（配合索引人工复核） |
| `verify-merge.js <chunksDir> <snapshotFile> [chunks.json]` | 令牌级覆盖率：原条目的标识符/数值是否都还在 `merged-<块名>.md` 里；并核对覆盖表是否覆盖本块分配到的全部条目 |
| `verify-hard.js <chunksDir> <snapshotFile> [chunks.json]` | 在上一支基础上把缺失令牌分软缺/硬缺（子串命中，或按 `/ . -` 拆段后每段都在 → 软缺），只报硬缺并定位回原条目编号，明细写 `hard-missing.json` |
| `assemble.js <chunksDir> <keyFile> <snapshotFile> [chunks.json] [--out <文件>]` | 装配 staging：合并稿（按 `chunks.json` 键序）+ 快照之后新增的条目逐字保留；**不动原轨** |
| `assemble-and-swap.js <chunksDir> <keyFile> <archiveFile> <snapshotFile> [chunks.json] [--write]` | 装配 + 安全检查（无双花括号、条目全带 summary、条目数已减少、新增数相符）+ 备份 + 落盘 + 被取代原文逐字归档；默认只演练 |
| `unexpire.js <keyFile> <archiveFile> <edits.json> [--write]` | 过期审计落盘器：逐处字面替换，每处强制「唯一命中」与「新文无连续左花括号」校验，落盘前复读比对磁盘；默认空跑。替换表格式见 `tools/edits.example.json` |
| `ztail.js <会话.jsonl.zstd> [条数]` | 会话时间线：逐帧解多帧 zstd，统计 `turn/end` 的 reason、首末次报错时间、去重错误文案、最后几条用户输入 |
| `zscan.js <会话.jsonl.zstd>` | 扫出报错回合与 error payload（更原始的事件倾倒） |
| `zdump.js <会话.jsonl.zstd> [输出文件]` | 多帧 zstd 解包器（按魔数 `28 B5 2F FD` 切帧、逐帧解） |
| `msgsrc.js <解压后的.jsonl>` | 打印用户消息的来源与形状（判定消息出自哪个渠道） |

`chunks.json` 形如 `{"C1":[2,7,9],"C2":[1,3]}`：键即块名（**键的顺序即装配顺序**），值是该块覆盖的原条目编号（1 起算）。
`ztail.js` 的时间默认按本机时区显示，设 `DSH_TOOLS_TZ=Asia/Shanghai` 可固定。
